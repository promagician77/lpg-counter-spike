Why line-crossing, not per-frame counting

Per-frame counting says "I see 5 cylinders right now." But that number jumps when one cylinder occludes another, when the camera shakes, or when new cylinders arrive mid-frame. The cashier would see the count flicker between 4 and 6.

Line-crossing says "3 cylinders have crossed this line so far." The count only goes up. Each crossing is logged with its track ID, size, and confidence, so it's auditable. If the cashier disagrees, they correct it in the UI, and both numbers are stored.

I found a real bug while writing the tests: an object that jitters back and forth near the counting line (vibration, wind, unsteady hand) can cross the line twice. The fix is a state machine — the object must be "armed" by being clearly on the before-side first, then counted when it reaches the after-side. Once counted, it can't be counted again. Test five proves this works.

Handling the hard cases you mentioned

  • Occlusion (cylinders hiding each other): ByteTrack keeps a stable ID through short occlusions — if a cylinder disappears for a few frames and reappears, it gets the same ID back and isn't double-counted. For longer occlusions, the line-crossing approach helps because it only counts the crossing moment, not every frame.
  • Dirty or damaged cylinders: the model needs to be trained on images of real dirty cylinders from your plant, not just clean stock photos. I'd spend the first few days on-site collecting varied training data. The height-ratio check in classify_size.py acts as a backup when the visual classifier is uncertain.
  • Varying lighting: augmentation during training (brightness, contrast, shadow overlays) helps. A fixed camera position also helps, since the lighting variation at one spot is bounded. I'd add an IR illuminator for night or low-light conditions.

Size classification

Two methods working together. First, the YOLO model itself classifies each detection into 20lb, 30lb, or 100lb — separate classes, not just "cylinder." Second, a height-ratio check: with the camera at a fixed distance, the pixel height of a cylinder maps to its real-world height. If the model says 20lb but the height says 100lb, the system flags it for the cashier. The tests for this are in test_classify.py.

The audit trail

Every transaction stores both the AI result and the cashier's final count. If the cashier corrects the AI, the correction is logged separately with a reason and timestamp. This matters for disputes: "the camera said 12, the cashier confirmed 14, and here's the video clip." The schema is in db/001_schema.sql.

Architecture on the Jetson

CCTV camera (RTSP)
    │
    ▼
Jetson Orin Nano (8GB)
    ├── YOLOv8n → TensorRT engine (~30 fps at 640×640)
    ├── ByteTrack (object tracking)
    ├── CylinderCounter (line-crossing)
    └── FastAPI server (local)
            │
            ▼
    Cashier touchscreen (browser)
    ├── Live count display
    ├── Confirm / correct
    ├── Transaction history
    └── Audit log

The model runs on the Jetson's GPU via TensorRT. The touchscreen connects over the local network to a FastAPI server on the same Jetson. No cloud dependency — everything works if the internet is down.
